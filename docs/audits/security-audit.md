# SquidCloud Security Audit (Pre–Open Source)

**Date:** 2026-11-10 (repo state: `fresh-main` @ `18b6e245`, working tree had untracked `supabase/functions/send-diwali/`)  
**Scope:** Read-only audit of the tracked repo, local git metadata, and live production metadata queried via Supabase Management API (`/v1/projects/aouqcwbdoyrccjcrhzzi/database/query`, token `sbp_…4f30`, 44 chars).  
**Audience:** Maintainers preparing this repository for public/open-source release.

> **Secret handling in this report:** secret values are redacted to first 6 chars + total length (e.g. `ghp_ml…` len 40). Do not treat redaction here as remediation — any value ever committed must be considered compromised and rotated.

---

## Executive Summary

This codebase is **not yet safe to publish as-is**. The most severe risks are **historical secret leakage in git** (service-role JWT, GitHub token, admin credentials, payment and KZA secrets committed in `.env` blobs), **a tracked HAR archive containing live bearer tokens**, **a GitHub PAT embedded in a local git remote URL**, and **database functions with dangerous privileges/exposure** (`public.exec_sql` and `public.get_secret` are `SECURITY DEFINER` and granted `EXECUTE` to `PUBLIC`; `get_secret` returns decrypted values from `vault.decrypted_secrets`). Several privileged edge functions are deployed/configured with `verify_jwt = false` or permissive CORS; some implement their own auth, but the trust boundary is inconsistent and easy to regress. RLS is enabled on all public tables (0 tables with RLS off), yet multiple policies are effectively world-readable/writable (`USING (true)` / `WITH CHECK (true)` for `public`, `authenticated`, or `service_role` roles as noted below).

**Blocking before open-source:** rotate/revoke every credential that ever appeared in git or the HAR, purge secrets and the HAR from git history (filter-repo/BFG) and force-push rewritten refs, remove the PAT from `.git/config` remotes, rotate DB password/API keys and re-issue Supabase tokens, lock down `exec_sql`/`get_secret` grants and review all `SECURITY DEFINER` functions, and re-audit edge-function auth + webhook signature verification.

## Detailed Notes

### 1) Committed/Leaked Secrets (Git & Artifacts)
- **`.env` in history (critical):** added/modified in commits including `d6fb599f`, `bc5f69a5`, `97a99526`, `407c7fad`, `07425642`. Reconstructed values (redacted): `VITE_SUPABASE_URL=https:…` (34), `VITE_SUPABASE_ANON_KEY=eyJhbG…` (208), `SUPABASE_SERVICE_ROLE_KEY=eyJhbG…` (219), `MXLPY_API_KEY=pk_liv…` (35), `GITHUB_TOKEN=ghp_ml…` (40), `ADMIN_ACCESS_KEY=frkf39…` (16), `ADMIN_USER_ID=654321` (6), `ADMIN_PASSWORD=frp_ad…` (24), `VITE_KZA_CLIENT_SECRET=efec03…` (64), `VITE_KZA_CLIENT_ID=squidc…` (10), `KZA_ADMIN_EMAIL=hellos…` (22). `GEMINI_API_KEY=your-g…` (17) appears placeholder-like in sampled blob — still rotate if ever real.
- **Tracked HAR:** `squidcloud.vercel.app_Archive [26-10-12 23-39-13].har` embeds anon JWT values and full traffic capture; may contain session cookies/user data beyond what was spot-checked.
- **Local-only but high risk:** `.env.local` contains `SUPABASE_SERVICE_ROLE_KEY` (219), `SUPABASE_URL`, `CRON_SECRET` (40), `VERCEL_OIDC_TOKEN` (long JWT) — gitignored, not tracked (verified), but must remain out of commits and be rotated if exposed.

### 2) Edge Function Auth Posture (Selected)
- **`admin-data-access`** (`verify_jwt=false`): custom gateway accepts any authenticated user and uses service role; likely broken authz boundary. **High.**
- **`admin-auth`** (`verify_jwt=false`): multi-step checks against `ADMIN_ACCESS_KEY`/profile/admin credentials via PREL context — sensitive; requires careful review of all steps and brute-force protections.
- **`api-file-*`**: API-key based (`cb_` prefix, SHA-256 hash lookup, scope checks) — reasonable pattern but depends on key storage/RLS and correct `verify_jwt=false` deployment; `api-file-upload` persists `encryptionKey` to DB (`encryption_key` column) — ZK implications.
- **`create-repos`** (`verify_jwt=false`): manually verifies bearer JWT with `auth.getUser` — acceptable if consistently enforced.
- **`github-storage`**: has a GET `?action=fix-cors` maintenance route that configures B2 CORS using server credentials — ensure this cannot be triggered by unauthenticated callers in production.
- **`maxelpay-webhook`** (`verify_jwt=false`): webhook — must cryptographically verify MaxelPay signature; audit full implementation for spoofing/replay.

### 3) Database Security (Live-Verified)
- RLS disabled on public tables: **none**.
- `USING/WITH CHECK = true` policies exist (20 rows returned) — review each for intent, especially `{public}` and broad `{authenticated}` cases.
- `SECURITY DEFINER` functions: many; notable exposures `exec_sql`, `get_secret` granted to `PUBLIC`. `squidveil.purge_expired` has null `proconfig`.
- `exec_sql` body currently no-ops but privilege is dangerous; `get_secret` is directly sensitive.

### 4) Client-Side Crypto / XSS / CORS
- ZK claim requires that encryption keys never leave client in recoverable form; DB write of `encryption_key` in API upload path is a red flag to resolve.
- `dangerouslySetInnerHTML` limited to 3 sites — verify sanitization/trust.
- Widespread `Access-Control-Allow-Origin: *` — acceptable only for carefully chosen public endpoints.
